# タスク: 実装を設計書と照らして独立にレビューする

あなたは、この実装を作った人物の意図を知らない独立したレビュアーである。
**`findings.md` 以外のファイルを作ったり編集したりしてはならない。**

検証器（`bash scripts/verify.sh`）は「設計IDが実装に**現れている**か」と試験・型検査・DB の移行が通るかしか見ていない。
**あなたの仕事は、検証器が見ていないもの —— 実装が設計書どおりか —— を見ることである**（設計書 13.6）。

## 見るもの

変更は未コミットのことが多い。`git status --short` で追加・変更されたファイルを確かめ、`git diff` と、
追加されたファイル（`git diff` に出ない）の中身を読む。コミット済みなら `git log --oneline -20` と `git diff <基>..HEAD`。

正は `docs/pmt-design.md`（設計書）と `docs/pmt-requirements.md`（要求仕様書）である。次の順に確かめる。

1. **検証器の弱体化**（最優先）
   - 試験の削除・skip・`xfail`・アサーションの緩和、`--passWithNoTests` などで試験 0 件を通す細工
   - `spec-ids.toml`・`trace.toml`・`scripts/verify.sh`・`scripts/setup-dev.sh`・設計書・要求仕様書・型検査の設定の変更
   - **中身の無い宣言**：`# RULE-…` の直後が `pass`・`TODO`・`NotImplementedError`、`"""API-…"""` の関数が固定値を返すだけ、
     `data-screen-id` だけの空の画面、試験が ID を docstring に書いただけで何も確かめていない
2. **計算ルールが設計書 5 章どおりか**（`backend/app/domain/`）
   - 5.4 の稼働日の軸（報告日線は報告日の終業＝原点から報告日までの稼働日の数、表示の日付は添字 ⌈p⌉−1）
   - 5.5 の前進・後退計算（マイルストーンの位置、希望開始日の下限、フロート ≤ 0 がクリティカル）
   - 5.6 の進捗ポイント・特殊な描画・判定。**試験の基準（稲妻チャート.txt §6 の例：P＝5.25/12.6/10/10、12/06・12/13、遅れ・前倒し・未着手・完了）が試験にあるか**
   - 5.2 の WBS ID（W§4 の例 1.0・1.1・2.0、改番しない・新旧対応）、5.3 の 100%ルール、5.8 の ETC・EAC、要求仕様書 7 章の BR の既定値
3. **テーブル・API・画面が設計書の行どおりか**
   - 4.1 の列・一意制約・外部キー。6.2 のメソッドとパス・権限（9 章の表。サーバ側で判定しているか）・6.1 のエラーの形
   - 5.10 の状態遷移（本人の承認の禁止・確定した報告日の入力の拒否・基準の版を上書きしない）
   - 7.1 のルート・7.3 のガントの描画（暦日で描く・非稼働日の帯・イナズマ線の頂点の色）
4. **層と依存の向き**（設計書 1.3）：ドメインが DB・HTTP・`date.today()` に触れていないか。変更履歴が全ての書き込みで残るか
5. **回帰・範囲・安全**：前に通っていた振る舞いを壊していないか。R1 の範囲を超えた機能・秘密情報・利用者の名前が混ざっていないか

変更されたコードが呼ばれる経路は、`Grep` で呼び出し元を辿って確認すること。

## 成果物

`findings.md` を作成し、次の形式で書く。

```markdown
## 検証器の弱体化・中身の無い宣言
（該当なしなら「検出せず」と書き、何を見たかを 1 行添える）

## 設計書との食い違い（重大）
- <ファイル:行> — <設計書の節> と食い違う：<何が起きるか> / 再現条件: <入力・状態>

## 軽微な指摘

## 設計書の側の問題（Change Request の候補）
（設計書が曖昧・矛盾していて実装が決められなかった点）

## このレビューが見ていないもの
```

指摘は**再現条件つき**で書く。「良くない」だけの指摘はしない。
指摘ゼロを「問題なし」と書かない。見ていない範囲（読まなかったファイル・確かめなかった節）を必ず添える。
