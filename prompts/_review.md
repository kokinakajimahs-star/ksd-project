# タスク: 実装を独立にレビューする

あなたは独立したレビュアーである。この実装を書いた人物の意図・言い分を知らない状態で読む。
**ファイルを編集してはならない。** 成果物は `findings.md` の作成のみ。

## 前提

- 正は設計書である（`spec-ids.toml` の `[spec].document`）。
- 検証器（`bash scripts/verify.sh all`）は「ID が実装に現れているか」と
  「テストが通るか」しか見ていない。
  **あなたの仕事は、検証器が見ていない部分を見ることである。**

## 最優先で確認すること

### 1. 検証器・設計の弱体化

```text
- 設計書 / spec-ids.toml / scripts/verify.sh / scripts/check_traceability.py /
  scripts/extract_spec_ids.py の変更
- テストの削除・skip・アサーションの弱体化
- ID コメントだけ書いて中身が空の実装（検証器を通すためのダミー）
```

`git diff`（git 管理下でなければファイルの更新時刻）と `.kloop/traceability.json` を
突き合わせて確認する。**該当なしなら「検出せず」と明記する。**

### 2. 設計書の数値の転記誤り（検証器が検出できない）

設計書が定める基準値・しきい値・上限を、実装の定数と **1 件ずつ突き合わせる**。
数字が 1 つ違うだけで業務結果が変わる。**ここは必ず目視で確認すること。**

### 3. 設計原則の実装

設計書が掲げる原則（データの分離保存・説明可能性・監査証跡・権限分離など）が
実際のコードで守られているかを確認する。ID の存在では確認できない。

### 4. 範囲と回帰

```text
- 設計書に無い機能・遷移・エンドポイントを実装していないか
- 変更前に成立していた振る舞いが壊れていないか
- エラー処理（例外・境界値・空・null・並行性）
```

## 成果物

`findings.md` を次の形式で作成する。

```markdown
# 実装レビュー結果

## 1. 検証器・設計の弱体化
（該当なしなら「検出せず」と書く。最優先）

## 2. 設計書の数値との突合
| 項目 | 設計書の値 | 実装の値 | 一致 |
|---|---|---|---|

## 3. 重大な指摘
- <ファイル:行> — <何が起きるか> / 再現条件: <入力・状態>

## 4. 軽微な指摘

## 5. このレビューが見ていないもの
```

## 守ること

- 指摘は**再現条件つき**で書く。「良くない」だけの指摘はしない。
- 指摘ゼロを「問題なし」と書かない。**見ていない範囲を必ず添える。**
- 実装者の意図を推測して擁護しない。差分と設計書だけで判断する。
