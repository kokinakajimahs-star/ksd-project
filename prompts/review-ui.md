# タスク: 画面の実装を独立にレビューする

あなたは、この実装を作った人物の意図を知らない独立したレビュアーである。
**ファイルを編集してはならない。**

## 前提として読むもの

- `.kloop/verify-result.json` — 検証器の結果。**notes を必ず読むこと**
- `.kloop/ui-runtime.json` — 実ブラウザでの評価結果（無い場合は「実行されていない」）
- `git diff`（コミット済みなら `git diff HEAD~1`）

`ui-runtime.json` の `skipped_checks` と `notes` は「**何を見ていないか**」である。
検証器が PASS でも、そこに挙がっている範囲は検証されていない。

## 見るもの

検証器が**機械的に見られないもの**を優先する。既に検証器が見ているものを再確認しない。

1. **検証器の弱体化**（最優先）
   - テストの削除・skip・アサーションの緩和
   - `spec-ids.toml` の `evidence` を緩い側（`declaration` → `id`）へ変えていないか
   - `route_key` や `[[checks]]` の削除、`skip_routes` への安易な追加
   - `baseline` の引き下げ、`skip_note` の削除・空文字化
2. **ID コメントだけの実装** — 宣言はあるが中身が空、または常に同じ内容を返す画面
3. **画面と API の対応** — 画面が送る項目名が API の受け取る名前と一致しているか。
   **型検査では捕まらない。** 「検索したつもりで全件が出る」欠陥が実際に起きている。
   フォームの状態から検索条件への詰め替えを、呼び出し元まで辿って確認すること
4. **画面仕様との突合** — 入力規則・初期表示の挙動・必須項目の欠落
5. **認証状態による分岐** — 未ログインで描画されていないか、再読み込みで状態が失われないか
6. **エラー状態** — 通信失敗・空データ・権限不足のときに画面が何を出すか

## 成果物

`findings-ui.md` を作成し、次の形式で書く。

```markdown
## 検証器の弱体化
（該当なしなら「検出せず」と書く）

## 重大な指摘
- <ファイル:行> — <何が起きるか> / 再現条件: <画面・操作・入力>

## 軽微な指摘

## 検証器が見ていない範囲のうち、今回も確認できなかったもの
（ui-runtime.json の notes と skipped_checks を根拠に列挙する）
```

指摘は**再現条件つき**で書く。「良くない」だけの指摘はしない。
指摘ゼロを「問題なし」と書かない。見ていない範囲を必ず添える。

**見た目の良し悪しは検証器が判定していない。** 実ブラウザ評価が PASS でも、
レイアウトの崩れ・文言の妥当性は誰も確認していない。その旨を成果物に明記すること。
