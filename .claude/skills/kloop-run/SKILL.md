# kloop run を使う

`kloop` は「停止条件・進捗判定・振動検出・予算」を外側から強制する有界ループである。
1 反復 = `claude -p` 1 回（**新しい context**）＋ 検証器 1 回。

このスキルは 4 つの用途を持つ。**どれをするかを最初に決める。**

| 用途 | LLM 消費 | 入口 |
|---|---|---|
| 1. 既存 run の参照・要約 | 無し | §1 |
| 2. mock で配線を確かめる | 無し | §2 |
| 3. 実機で回す | **有り** | §3（**dry-run で確かめる。費用の承認は取らない**） |
| 4. 中断・承認待ち・人の応答待ちからの再開 | 場合による | §4 |

## 絶対に守ること

- **実機の run の前に費用の承認は取らない**（ksd-ls の Q-LS-34・LS-D32。CR-090）。使った量（`run.json` の `usage_total`）を報告に出す
- **mock の結果を実行結果として報告しない。** レポートに `backend: mock` と出ていたら必ずそう言う
- **`SUCCESS` 以外を「失敗」とまとめない。** 終了状態ごとに次のアクションが違う（§5）
- **検証器（`scripts/verify.sh`）を、テストを通すために書き換えない。** kloop が保護パスとして検出し `POLICY_DENIED` になる
- **`/tmp` を作業ディレクトリにしない。** WSL の再起動で消える

## 環境

```bash
KLOOP="${KLOOP_BIN:-kloop}"   # PATH の kloop（ksd-ls の venv の入口）。KLOOP_BIN で実体を指定できる
```

`kloop` は Python 3.11+ 標準ライブラリと git のみに依存する。`jq` は不要。

## 1. 既存 run を参照・要約する（既定の入口）

まず**すでに結果があるか**を確認する。回し直す必要がないことは多い。

```bash
$KLOOP status --last 5
$KLOOP report --run-id <run_id>
```

`report` は「結果 / 収束の推移 / 未達の項目 / 試した手段 / **このレポートが見ていないもの** /
推奨する次のアクション」を出す。**そのまま会話へ貼らない。** 読んだうえで、利用者の質問に
答える形にまとめ直す。深掘りが要るときだけ `.kloop/runs/<run_id>/iterations/` を読む。

## 2. mock で配線を確かめる（LLM を呼ばない・無料）

```bash
$KLOOP doctor
$KLOOP doctor --probe-verify      # 検証器を 1 回起動して結果 JSON の契約を見る（副作用あり）
$KLOOP run <タスク> --backend mock
```

配線・検証器の契約・終了状態の出方を確認するために使う。**AI の代用ではない。**

`--probe-verify` が `verify.probe` / `verify.probe.progress_metrics` に WARN を出したら、
**その run は合否が exit code だけで決まり、宣言した進捗指標は使われない**（指示書 §5.4 / §4.3）。
実機で回す前にここで潰す。

## 3. 実機で回す

### 手順（この順を崩さない）

```bash
# 3-1. 診断（NG があれば解消するまで進まない）
$KLOOP doctor

# 3-2. 見積り（backend を呼ばない）
$KLOOP run <タスク> --dry-run
```

3-2 の出力（上限・起動形・1 反復目のプロンプト・費用上限）で設定の誤りを確かめる。
**回す前の費用の承認は取らない**——利用者の同意を待たずに 3-3 へ進む。

```bash
# 3-3. 実行（時間がかかる。タイムアウトを長く取る）
$KLOOP run <タスク> -v

# 3-4. 要約
$KLOOP report --run-id <run_id>
```

### 上限をその場で変えたいとき

```bash
$KLOOP run <タスク> --max-iterations 5 --max-budget-usd 2.0
```

**「収束しないから反復回数を増やす」は最後の手段である。** 先に
(1) 検証器が根本原因を出せているか、(2) タスクが大きすぎないか、(3) プロンプトが誤った
前提を与えていないか、を確認する。

## 4. 中断・承認待ち・人の応答待ちから再開する

```bash
$KLOOP resume --run-id <run_id>
$KLOOP resume --run-id <run_id> --answer "<人の応答>"      # NEEDS_HUMAN で中断した run
```

`NEEDS_HUMAN` は人の応答を待つ中断である。応答は**人から受け取ったものだけ**を渡し、エージェントが自分で応答を作らない。
応答の無い再開は何も実行しない。応答は検証器の判定を変えず、同じ理由で人の判断が要れば再び中断する。
グラフで承認ゲートを通った後なら、承認も同じ呼び出しで渡し直す（kloop が表示する再開のコマンドをそのまま使う）。

設定またはプロンプトが変わっていると**再開しない**（結果が混ざるため）。その場合は新しい run を開始する。

## 5. 終了状態ごとの次アクション

| 終了状態 | 意味 | 次にすること |
|---|---|---|
| `SUCCESS` | 検証器が PASS した | 差分をレビューする。**「見ていないもの」を必ず添える** |
| `BLOCKED_NO_PROGRESS` | 進捗が止まった | 検証器・分解・プロンプトを見直す。反復数を増やさない |
| `BLOCKED_OSCILLATION` | 過去の状態へ戻った | 往復している 2 案を特定し、人が決める |
| `BLOCKED_MAX_ITERATIONS` | 反復上限 | 推移が右肩下がりなら上限を上げる価値がある。横ばいなら無い |
| `BUDGET_EXCEEDED` | 費用上限 | 1 反復あたりのコストを確認する（model / effort / 読ませている量） |
| `TIMEOUT` | 時間上限 | 反復中は絞った検証器を使う構成に変える |
| `NEEDS_HUMAN` | 人の応答を待って中断（終わりではない） | notes と未達項目を読み、`kloop resume --run-id <id> --answer <応答>` で応答して再開する。応答の無い再開は何もしない |
| `POLICY_DENIED` | 不変条件違反・保護パス改変 | **成果物をそのまま採用しない。** 差分を必ず人が確認する |
| `ENVIRONMENT_ERROR` | 設定・検証器・backend の問題 | `kloop doctor` |

## 6. 結果を報告するときの言い回し

| 書かない | 書く |
|---|---|
| 「修正が完了した」 | 「検証器は PASS した。検証していない範囲は別途記載した」 |
| 「問題なし」 | 「この run が検証していないもの」を必ず添える |
| 「N 件のバグを直した」 | 「failures が N 件減った。個々の妥当性は人が判定していない」 |
| （mock の結果を実行結果として） | 「これは mock の結果であり、実機の Claude は呼ばれていない」 |

- 上限で省略した件数、代理指標に落ちた判定、未検証の項目は**黙って落とさない**
- コストはクライアント側の推定値であり、課金額の正ではない

## 7. `/goal` との使い分け

対話セッション内で完結し、fresh context も機械可読メトリクスも要らないなら、
**組み込みの `/goal` の方が簡単で速い**。

```text
/goal すべてのテストと型検査が通ること。テストを削除・弱体化しないこと。5 回試して駄目なら停止。
```

`kloop` を使うのは次の 4 つのいずれかに当てはまるときである。

1. セッション外（CI / cron / headless）で回したい
2. 反復ごとに fresh context を強制したい
3. 収束メトリクスを run 間で比較したい
4. 停止条件・予算を決定論的に強制したい
