# セッション内で収束させる

`kloop` を持ち出すまでもない場合の手順。**まずこれを試す。**
外側プロセスも状態ファイルも要らないぶん、速くて安い。

## 使い分け

このスキルで足りる場合：

- 1 セッションで終わる規模である
- fresh context の強制が要らない
- 収束メトリクスを run 間で比較しなくてよい

`kloop-run` へ切り替える場合（指示書 §6.7）：

1. セッション外（CI / cron / headless）で回したい
2. 反復ごとに fresh context を強制したい
3. 収束メトリクスを蓄積・比較したい
4. 停止条件・予算を決定論的に強制したい

## 手順

### 1. まず観測する（編集しない）

```text
検証器を実行して、失敗の全文を読んで。まだ編集しないで。
根本原因の仮説を、根拠となる出力とともに挙げて。
```

根本原因の見立てが妥当そうなら次へ進む。**ここを飛ばすと、対症療法を反復して収束しない。**

### 2. 目標を設定する

```text
/goal $ARGUMENTS が通ること。
テストの削除・スキップ・弱体化、しきい値の引き下げ、型検査や lint の無効化、
検証スクリプト自体の変更をしないこと。5 回試して駄目なら停止すること。
```

`/goal` は、Claude が停止しようとするたびに別の評価器が条件充足を判定し、
未達なら作業へ戻す。**必ず試行回数の上限を条件に含めること。**

### 3. 不変条件（毎回そのまま伝える）

```text
次のいずれかによって検証を通過させてはならない：
- テストの削除・スキップ・無効化
- アサーションの弱体化
- カバレッジ・品質しきい値の引き下げ
- 型検査・lint ルールの無効化
- 本番の振る舞いをスタブ・ハードコードで置き換えること
- 検証器そのもの（verify スクリプト・CI 設定）の変更
これらが必要だと判断した場合は、実施せずに理由を報告して停止すること。
```

### 4. 進捗が止まったら

同じ方針を 2 回繰り返して改善が無い場合、**反復を増やさない**。次の順で見直す。

```text
1. より良い検証器      … 失敗の原因が出力から分かるか
2. より良い状態表現    … 何が変わったかを機械的に測れるか
3. より良い分解        … 1 反復の作業が大きすぎないか
4. より良いコンテキスト … 必要なファイルを見せているか
5. より良いプロンプト
6. より多い反復回数    ← 最後
```

### 5. 独立レビューを挟む

生成した本人に自己採点させない。**別の context** でレビューさせる。

```text
差分を、会話履歴を引き継いでいない独立したレビュアーとして見て。
実装の意図は考慮せず、差分だけから回帰・見落とし・検証器の弱体化を探して。
```

サブエージェント（`loop-reviewer`）または `context: fork` の Skill を使うと、
会話履歴から隔離された状態でレビューできる。

## 報告

- 「通った」ではなく「**検証器が通った**」と書く。検証していない範囲を必ず添える
- 上限に達して止めた場合は、状態・満たせていない基準・試した方針・根拠・
  人間に求める判断を並べる。「できませんでした」で終わらせない
