## なぜ ID を使うのか

反復を機械的に回すには「どこまで進んだか」を人手を介さず測る必要がある。
設計書に ID（画面 ID・API ID・ルール ID・テーブル名など）が振ってあれば、
**「設計書の ID のうち実装に現れていないものの数」**を進捗指標にできる。
この数が単調に減ることが「実装が進んでいること」の定義になる（kloop 指示書 §4.3）。

## 1. 調査：設計書で見るもの

`--survey` は設計書を走査して、ID らしきパターンとその件数・接頭辞の内訳・章構成を出し、
`spec-ids.draft.toml` を書く。**これは候補を挙げただけである。**
続けて**あなたが設計書を読む**。見るべきところ:

| 見るもの | 何を判断するか |
|---|---|
| 章構成（目次） | どの章が「実装すべきものの一覧」か |
| ID を含む表 | 表の列構成（ID / 名前 / パス / ルーティング …）。抽出の正規表現を決める |
| 実装ガイドの章 | 技術スタック、リポジトリ構成、実装規約、推奨開発順序 |
| テスト方針の章 | 何をもって「実装済み」とするか |
| 未確定事項の章 | `docs/open-questions.md` へ移すもの |
| 状態遷移図 | 状態コードの一覧（mermaid から抽出できることが多い） |

**survey の候補をそのまま採らない。** 例えば「全大文字の識別子」は
ロール名・列挙値・見出し語まで拾うため、多くはノイズである。

## 2. `spec-ids.toml` の詳細

### 2.1 `target_dirs` と `evidence` の値

```toml
target_dirs = ["backend/app/api"]     # ここに evidence が現れれば実装済み
evidence = "declaration"               # ID が宣言の形で現れる（既定はこれを使う）
evidence = "declaration_and_test"      # 上記に加えてテストにも現れる（テストを必須にする）
evidence = "id"                        # ID 文字列がどこかにある（緩い。互換のために残す）
evidence = "id_and_test"               # 上記に加えてテストにも現れる
evidence = "regex"                     # 独自の判定式
evidence_regex = '__tablename__\s*=\s*["\x27]{id_lower}["\x27]'
evidence = "state"                     # 宣言に加えて**実環境の計画**を見る（インフラ）
```

`declaration` は「行頭に ID を書く」「属性・キーの値が ID」の形だけを実装と数える。
文中の参照は数えない。**既定は `declaration` を使うこと。**
中身が要る種別（判定ロジック・状態機械など）は `declaration_and_test` か `regex` を選ぶ。

試験を本体と同じディレクトリに置く言語（`*.test.ts`・`*_test.go` など）は、`test_globs` で試験を宣言する。
当たるファイルは `target_dirs` の中でも実装の証拠に数えない（`*_and_test` では試験の証拠に数える）。
glob はプロジェクトの根からの相対パスで、`**` は 0 個以上のディレクトリ。**命名から推し量らないので、人が書く**（CR-122）。

```toml
target_dirs = ["src"]
test_globs = ["src/**/*.test.ts", "src/**/*.spec.ts"]
```

### 2.2 `evidence = "id"` が緩い実例

**`evidence = "id"` は、ID をコメントに書くだけで実装済みになってしまう。**
意図せずそうなった実例がある。API 層の docstring に書かれた

```ts
/** 部品明細の入力値（設計書 8.5 `parts[]`、UI-SC-002 入力値（部品明細））。 */
```

という**正当な参照コメント**によって未実装数が減り、**画面が 1 枚も無いのに数字だけ良くなった。**

### 2.3 インフラ：`evidence = "state"`

インフラのように「書いただけでは存在しないもの」には `state` を使う。
**`.tf` は書けば存在するが、クラウド資源は `apply` して初めて存在する。**
ID コメントの直後に `resource` があることは、属性が要件どおりであることを何も保証しない。

```toml
evidence = "state"
state_source = "plan"                 # `terraform show -json <planfile>` の計画表現
state_file = ".kloop/plan.json"       # **kloop は terraform を実行しない。** 作るのは利用側
protected_attributes = [              # 弱化を検出する属性と向き（省略時は any）
  "google_storage_bucket.retention_policy.retention_period:decrease",
]
```

不可逆な変更（削除・置換）は `needs_human`、保護属性の弱化は不変条件違反になる。
**宣言した計画が無ければ失敗に数える**（実行していない検証は合格の根拠にならない）。

### 2.4 到達できること：`route_key`

画面のように「到達できること」が要件に含まれる ID には `route_key` を併用する。

```toml
route_key = "route"   # row の名前付きグループ名
```

ID の宣言があってもルートが定義されていなければ、**利用者は到達できない**。
これを注記ではなく `failures` に数える。

### 2.5 baseline（設計書から抽出できるべき最小件数）

抽出結果の件数をそのまま入れる。**設計書を削って分母を減らす改変の検出に使う。**
不変条件 `spec_ids_not_reduced` として毎回検査される。

### 2.6 追加の検証（`[[checks]]`）とタスク（`[[extra_tasks]]`）

テスト・ビルド・IaC 検証を `[[checks]]` に、
ID では表せない作業（構成づくり・IaC）を `[[extra_tasks]]` に書く。

> `[[extra_tasks]]` には **`requires` を必ず書く。** 空だと検証器が何も見ずに PASS を返し、
> そのタスクが「何もせず成功」になる。

> `[[checks]]` の `reuse`（検証の結果の再利用。CR-094・CR-097）は**書かない。** 既定で写し、`reuse = false` がその検査を外す
> 人の宣言で、書くかは人が決める（鍵に入らない入力——リポジトリの外のファイル・時刻・無視されたファイル・印の無いネットワーク——が
> run の間に変わりえて合否がそれに依る検査と、不安定な試験を外す。指示書 §12.2）。外すべきと思う検査があれば、人へ挙げる。

> サンドボックスの中で `~/.config`・`~/.cache` へ書く CLI（firebase-tools など）を使う検査には `env = { XDG_CONFIG_HOME = "{check_tmp}/xdg" }` を書く（CR-126。`allowWrite` は広げない）。

### 2.7 検算

`spec-ids.toml` を書いたら、**設計書に書かれている件数と一致するか**を確かめる。

```bash
cd <対象ディレクトリ> && python3 scripts/extract_spec_ids.py    # bootstrap 後に使える
```

設計書が「全 45 画面」と書いているのに 43 件しか取れないなら、正規表現が
表の一部の書式（セル内に複数の記載があるなど）を取りこぼしている。**必ず合わせる。**

## 4. 適用した後にあなたが埋めるもの

| ファイル | 埋めるもの |
|---|---|
| `prompts/_preamble.md` | プロジェクト名・設計書名・技術スタック・禁止事項（`<CHANGE-ME …>` の印） |

## 5. 設計書へ追記する章の雛形

**設計書の変更なので、必ず承認を得てから行う。**
設計書に次が書かれていないと、実装ループが判断に迷う。追記を提案する。

```markdown
# N. <ツール名> による実装ループ

## N.1 進捗の測り方
設計書の ID のうち実装に現れていないものの数を進捗指標とする。

## N.2 実装ループの原則
- 設計書の記載を「正」とする。記載の変更が必要と判断されるまで、確認を待たずに反復する
- 未確定事項は停止理由にならない（抽象化・外部設定化・fail fast・記録の 4 点セット）
- ループを抜ける唯一の条件（技術的に不成立／完了条件を満たせない／矛盾／
  セキュリティ違反／前提値の不成立）
- 承認ゲート（不可逆操作・課金・公開・設計書の変更）

## N.3 実装規約（機械検証可能な形式）
| 種別 | 設計書での ID | 実装に現れるべき形 | 検証対象ディレクトリ |

## N.4 タスク分割
## N.5 完了条件（Definition of Done）
## N.6 検証器が見ていないもの   ← **必ず書く**
```

`N.6` は特に重要である。ID の存在は実装の正しさを意味しない。
検証できないもの（業務的な妥当性・数値の転記誤り・視覚的な一致・外部サービスの挙動）を
明記し、人のレビューへ回す。

追記したら **`spec-ids.toml` の `[spec].loop_chapter` に章番号を書く**。

## 6. UI 設計資料（PPTX）

画面が PowerPoint の**図形・テキスト**で描かれていれば、項目名・ボタン・一覧列を抽出できる。

```toml
[spec]
ui_pptx = "UI設計_全画面.pptx"
```

`docs/ui/<画面ID>.md` と `docs/ui/_common-layout.md` が生成され、UI タスクのプロンプトが参照する。
さらに **PPTX の画面 ID と設計書の画面 ID が一致すること**が不変条件になる
（成果物間の整合を実装以前に検証できる）。

画面が**画像**で貼られている場合は抽出できない。その旨を報告し、
「視覚的な一致は検証できない」と限界に加える。

## 7. 報告の書式

```markdown
## 構築した環境

- 設計書: <ファイル名>（<行数>行）
- ID 体系: 画面 45 / API 91 / ルール 19 / テーブル 35 / 状態 20 = 210 件
- 未実装 ID の初期値: N 件（これが 0 を目指す数）
- タスク: M 件（`kloop run <タスク>` で個別に回せる）
- 検証器: `bash scripts/verify.sh <scope>`

## 判断したこと
（ID 体系の選択、実装との対応、物理名の規約など。ASSUMPTIONS.md へも記録した）

## この環境が保証していないもの
- **ID が実装に現れていることと、その実装が正しいことは別である**
- 設計書の数値の転記誤りは検出できない
- （UI 資料がある場合）色・罫線・余白などの視覚的な一致
- 実行しなかったチェック（skipped_checks）
```

**「セットアップ完了」で終わらせない。** 何を測れて何を測れないかを必ず添える。

## 8. つまずいたとき

| 症状 | 原因 | 対処 |
|---|---|---|
| 抽出件数が設計書の記載と合わない | 表の書式に例外がある（1 セルに複数記載など） | `row` の正規表現を直す。セル全体を取ってから中身を分解する |
| survey が大量の候補を出す | 一般的な大文字語まで拾っている | 意味のあるものだけを `[[kinds]]` にする |
| タスクが細かすぎる／大きすぎる | 自動分割の判断（グループ数と件数） | `split_by_group = true/false` で明示的に指定する |
| `verify.sh <scope>` が即 PASS する | `[[extra_tasks]]` の `requires` が空 | 成果物のパスを列挙する |
| ループが「ID を書くだけ」で進む | `evidence = "id"` が緩い | `declaration` / `declaration_and_test` / `regex` へ変える |
| 実装が無いのに未実装数が減る | `evidence = "id"` が別ファイルの参照コメントを数えている | `declaration` へ変える。notes にこの緩さが出ている |
| 画面はあるが利用者が辿り着けない | ルートを検証していない | `route_key` を指定する |
| 設計書に ID が無い | 設計書の性質 | SKILL.md §1 の 2 択を提案する |
