# 設計書から実装環境を組み立てる

設計書 1 本から、**kloop で反復実装できる状態**を作る。

```text
設計書（大きい・1 セッションで実装しきれない）
   ↓  ID 体系を見つける          ← ここが判断。あなたの仕事
   ↓  ID ↔ 実装の対応を決める     ← ここも判断。あなたの仕事
   ↓  kloop bootstrap             ← 機械的。コマンドの仕事
検証器・タスク・プロンプト・グラフ・承認ゲート
```

進捗は**「設計書の ID のうち実装に現れていないものの数」**で測る（単調に減る＝実装が進んでいる。kloop 指示書 §4.3）。

詳細（表・設定の例・雛形・実例）は同じディレクトリの `reference.md` にある。**全文で読まない。**
各手順の「→」の行が指す節だけを、そのときに読む。

## 絶対に守ること

- **設計書を勝手に書き換えない。** §5 の追記を提案する場合も、必ず承認を得てから行う
- **`--dry-run` の結果を利用者に見せてから適用する**
- **ID の存在は実装の正しさを意味しない。** この限界を必ず報告に含める
- 生成物（`prompts/*.md`、`docs/spec-ids.json`、`docs/ui/*.md`）は**手で編集しない**。
  変更は `spec-ids.toml` か生成スクリプトへ加える
- **`/tmp` を対象ディレクトリにしない。** WSL の再起動で消える

## 環境

```bash
KLOOP="${KLOOP_BIN:-kloop}"   # PATH の kloop（ksd-ls の venv の入口）。KLOOP_BIN で実体を指定できる
```

## 1. 調査（設計書を読む）

```bash
$KLOOP bootstrap <対象ディレクトリ> --survey
```

ID の候補・件数・章構成を出し、`spec-ids.draft.toml` を書く。**候補を挙げただけなので、そのまま採らない**（多くはノイズ）。
続けて**あなたが設計書を読み**、何を実装し、何をもって実装済みとするかを見極める。

→ 設計書のどこで何を判断するか：`reference.md` §1

設計書に ID 体系が無いなら、次のどちらかを利用者へ提案する。

1. 設計書へ ID を振る（**設計書の変更なので承認が要る**）
2. ID を使わず、テスト・ビルドの成否だけを検証器にする（進捗は「作業ツリーの変化」の代理指標になり、精度は落ちる。kloop 指示書 §4.3）

## 2. `spec-ids.toml` を書く

`spec-ids.draft.toml` を整えて `spec-ids.toml` として保存する。
書式と全項目の説明は `<CHANGE-ME>/templates/bootstrap/spec-ids.toml` にある（実例つき）。決めるのは次の 4 つ。

1. **どの ID 体系を採るか**：意味のあるものだけを `[[kinds]]` にし、ノイズは消す
2. **各 ID を実装のどこへ対応させるか**（`target_dirs`・`evidence`）
   - **既定は `evidence = "declaration"`。** `"id"` は ID をコメントに書くだけで実装済みになる
   - 中身が要る種別（判定ロジック・状態機械）は `declaration_and_test` か `regex`
   - インフラ（書いただけでは存在しないもの）は `state`。**計画が無ければ失敗に数える**
   - 到達できることが要件の ID（画面）は `route_key` を併用する
   - → `reference.md` §2.1 値の一覧・§2.2 `"id"` の実例・§2.3 `state`・§2.4 `route_key`
3. **baseline**：抽出件数をそのまま入れる（設計書を削って分母を減らす改変を検出する。→ `reference.md` §2.5）
4. **`[[checks]]`（テスト・ビルド・IaC の検証）と `[[extra_tasks]]`（ID で表せない作業）**。
   **`[[extra_tasks]]` には `requires` を必ず書く。** 空だと検証器が何も見ずに PASS を返す（→ `reference.md` §2.6）

**検算：抽出件数を設計書に書かれている件数と必ず合わせる**（「全 45 画面」で 43 件なら正規表現の取りこぼし）。
→ 検算のコマンド：`reference.md` §2.7

## 3. 計画を提示する

```bash
$KLOOP bootstrap <対象ディレクトリ> --dry-run
```

ID 体系・件数・生成されるタスク・生成されるファイルが出る。**まだ何も書いていない。**
これを利用者へ提示し、次を確認してもらう。

- ID の件数は設計書と合っているか
- タスクの粒度は妥当か（細かすぎ／大きすぎ）
- 実装の対応先（`target_dirs`）は正しいか

## 4. 適用する

```bash
$KLOOP bootstrap <対象ディレクトリ>
```

既存ファイルは上書きされない（衝突は `.kloop-new` に出る）。抽出とプロンプト生成まで走る。続けて確認する。

```bash
cd <対象ディレクトリ>
bash scripts/verify.sh all      # 未実装 ID の初期値（これが 0 を目指す数）
$KLOOP doctor                   # NG が無いこと
$KLOOP doctor --probe-verify    # 検証器を 1 回起動し、結果 JSON の契約（§5.2）を見る
```

WARN は黙って起きるので**ここで潰す**：`verify.probe` なら合否が exit code だけで決まり（§5.4）、
`verify.probe.progress_metrics` なら宣言した進捗指標が 1 度も使われない（§4.3）。

そのあと**あなたが** `prompts/_preamble.md`・`CLAUDE.md`・未確定事項の台帳・判断の記録などを埋める。
→ 埋めるファイルと中身：`reference.md` §4

## 5. 設計書へ実装ループの規約を追記する（提案）

**設計書の変更なので、必ず承認を得てから行う。** 規約が無いと実装ループが判断に迷う。

→ 追記を提案する章の雛形（N.1〜N.6）：`reference.md` §5

**N.6「検証器が見ていないもの」は必ず書き**、人のレビューへ回す。追記したら `[spec].loop_chapter` に章番号を書く。

## 6. UI 設計資料（PPTX）がある場合

`[spec].ui_pptx` に指定すると画面の項目を抽出し、設計書との画面 ID の一致を不変条件にする（→ `reference.md` §6）。

画面が**画像**で貼られている場合は抽出できない。その旨を報告し、「視覚的な一致は検証できない」と限界に加える。

## 7. 報告する

`reference.md` §7 の書式で、構築した環境・判断したこと（ASSUMPTIONS.md へも記録）・**この環境が保証していないもの**
（少なくとも：ID の存在と実装の正しさは別・数値の転記誤り・UI 資料があれば視覚的な一致・skipped_checks）を報告する。

**「セットアップ完了」で終わらせない。** 何を測れて何を測れないかを必ず添える。

## つまずいたとき

→ 症状（件数が合わない・即 PASS する・ID を書くだけで進む など）の原因と対処：`reference.md` §8
